# خطة تطوير Suly AI إلى وكيل يخدم كل المستخدمين

آخر تحديث: 2026-11-14

## 1. من أين نبدأ اليوم

الأساس الموجود حاليًا ليس تجربة أولية، بل نواة وكيل حقيقية تعمل في الإنتاج:

| المكوّن | الحالة |
|---|---|
| تصنيف الطلب (دردشة / بسيط / مركب) | يعمل |
| حلقة وكيل بحدود خطوات ومحاولات | يعمل |
| سجل أدوات مركزي مع مخطط مدخلات وصلاحيات | يعمل |
| موافقة ذرية لمرة واحدة على العمليات الحساسة | يعمل |
| مساحة عمل دائمة للمهمة وحالاتها وخطواتها | يعمل |
| اختيار النموذج حسب الدور (planner / summarizer / reviewer) | يعمل |
| مراجع مستقل مع إعادة محاولة واحدة مرتبطة بالمراجعة | يعمل |
| سجل تنفيذ أدوات كامل (pending → running → completed/failed/rejected) | يعمل |
| نشر فعلي لـ `ai-router` على Supabase | الإصدار 39 |

ما ينقص ليس «النواة»، بل **اتساع الأدوات وعمق التجربة والثقة والتشغيل على نطاق**.

## 2. الهدف النهائي

وكيل يستطيع أن يقول له أي مستخدم، بأي مستوى تقني:

> «اعمل لي كذا من أول لآخر، وأنا أتابع وأوافق على المهم.»

ويقدر ينفّذ فعليًا في مجالات مختلفة: دراسة، أعمال حرة، إدارة مشروع صغير، محتوى، بحث، بريد وملفات، تحليل بيانات، وأتمتة روتينية.

هذا الهدف يحتاج أربع طبقات مكتملة معًا: **أدوات**، **ذاكرة**، **استمرارية**، **ثقة**.

## 3. المراحل التنفيذية

### المرحلة أ — محرك أدوات قابل للتوسع

**المشكلة:** كل أداة جديدة اليوم تحتاج تعديل كود + تسجيل + نشر. هذا لا يتوسّع لخدمة كل الناس.

**الحل:**

1. فصل كل أداة في ملف مستقل باسم `tools/<name>.ts` فيه: الوصف، المخطط، الأثر، السياسة، محوّل التنفيذ.
2. سجل أدوات يُحمَّل تلقائيًا من المجلد بدل قائمة ثابتة.
3. عقد موحّد للأخطاء: `unavailable` / `unverified` / `failed` / `rejected` / `needs_approval`.
4. اختبار إلزامي لكل أداة يغطي: مدخلات صحيحة، مدخلات خاطئة، رفض بدون موافقة، فشل المزود.
5. أدوات داخلية آمنة: حاسبة، تحويل تواريخ، تلخيص ملف، جدول بيانات صغير.

**النتيجة:** إضافة خدمة جديدة = ملف واحد + اختبار + PR، من غير لمس منطق الوكيل.

### المرحلة ب — ذاكرة حقيقية للمستخدم

**المشكلة:** الوكيل يعرف الطلب الحالي فقط، وينسى تفضيلات المستخدم ومشاريعه.

**الحل:**

1. ذاكرة تفضيلات (لغة، أسلوب، قيود، جهات متكررة).
2. ذاكرة مشروع (ملفات، قرارات، مصطلحات خاصة).
3. ذاكرة مهام منتهية قابلة للاسترجاع بالتشابه الدلالي مع حدود صريحة.
4. تحكم كامل للمستخدم: عرض، تعديل، حذف، وتعطيل الذاكرة.
5. منع أي ذاكرة تحتوي مفاتيح أو بيانات حساسة عبر تنقية قبل الحفظ.

**النتيجة:** كل مرة يفتح المستخدم التطبيق، الوكيل يبدأ من حيث توقف، مش من الصفر.

### المرحلة ج — استمرارية المهام والتشغيل المجدول

**المشكلة:** المهمة الحالية تعيش داخل الطلب. لو المستخدم قفل التطبيق أو طالت المهمة، ما فيهاش متابعة مستقلة.

**الحل:**

1. عامل تنفيذ خلفي (queue + worker) يكمّل المهام الطويلة بدون اتصال المتصفح.
2. استئناف تلقائي بعد الفشل مع عدد محاولات محدود وسقف زمني.
3. مهام مجدولة: «كل صباح لخّص لي بريدي»، «كل أسبوع حدّث لي التقرير».
4. إشعارات عند: انتظار موافقة، اكتمال، فشل، تجاوز حد التكلفة.
5. إلغاء فوري حقيقي يوقف التنفيذ مش بس يسيب الطلب.

**النتيجة:** الوكيل يشتغل كخدمة مستمرة، مش كرد لحظي.

### المرحلة د — تكاملات بمستوى الخدمة

الأولوية حسب قيمة المستخدم اليومية:

1. **Gmail** — قراءة، بحث، تصنيف، مسودات، إرسال بموافقة. (البنية موجودة، ينقص اختبار حي.)
2. **Google Drive** — بحث، قراءة مستندات، إنشاء ملف.
3. **Google Calendar** — عرض، إنشاء، تعديل مواعيد.
4. **GitHub** — قضايا، Pull Requests، مراجعة كود.
5. **Google Sheets** — قراءة/كتابة جداول وتحليل بيانات.
6. **Notion / Tasks** — ملاحظات ومهام.
7. **WhatsApp / Telegram** (اختياري) — رسائل بموافقة صريحة.

لكل تكامل: صفحة ربط، حالة اتصال حقيقية، اختبار بحساب تجريبي، وسياسة موافقة واضحة.

### المرحلة هـ — قدرات تنفيذ أعمق

1. **بيئة تنفيذ معزولة**: تشغيل كود قصير داخل sandbox بحدود وقت وذاكرة وبدون شبكة افتراضيًا.
2. **معالجة ملفات**: PDF، Word، Excel، CSV — قراءة، تحويل، تلخيص، استخراج جداول.
3. **متصفح آلي** (مرحلة متقدمة): فتح صفحات، قراءة محتوى، تعبئة نماذج — بموافقة صريحة على كل خطوة كتابة.
4. **توليد مخرجات**: تقارير، عروض، صور — كمخرجات قابلة للتنزيل.

**قاعدة ثابتة:** أي قدرة جديدة تدخل بسجل أدوات، وكل عملية كتابة تحتاج موافقة.

### المرحلة و — تجربة المستخدم

1. عرض حي داخل المحادثة: الخطة، الخطوة الحالية، الأدوات المستخدمة، الوقت، التكلفة.
2. بطاقات موافقة واضحة: نص العملية بالكامل قبل التنفيذ، مع «موافقة» و«تعديل الطلب».
3. زر إيقاف/استئناف حقيقي.
4. سجل مهام قابل للبحث والاستعادة.
5. قوالب جاهزة لكل مجال: طالب، مستقل، متجر صغير، مدير مشروع، باحث.
6. شرح الفشل بلغة مفهومة مع خطوة تالية مقترحة، لا رسالة خطأ تقنية.

### المرحلة ز — الثقة والأمان

1. صلاحيات لكل مستخدم وكل تكامل على حدة (scopes).
2. سجل تدقيق لكل عملية كتابة: من، ماذا، متى، بأي موافقة.
3. حدود تكلفة يومية/شهرية لكل مستخدم مع تنبيه قبل التوقف.
4. عدم تخزين محتوى الرسائل الخام في سجلات الأدوات (مطبّق).
5. تنقية الأسرار قبل أي تسجيل أو عرض (مطبّق).
6. سياسة احتفاظ بيانات واضحة وإمكانية الحذف الكامل.
7. عزل بيئة التنفيذ لمنع أي وصول غير مصرّح.

### المرحلة ح — التشغيل على نطاق

1. طوابير وسقوف تزامن لكل مستخدم ولكل مزوّد.
2. مراقبة: زمن الاستجابة، معدل الفشل، تكلفة الطلب، معدل الموافقة.
3. حدود معدل النماذج مع fallback بين المزودين.
4. خطة طوارئ لانقطاع مزوّد (تعمل جزئيًا اليوم).

### المرحلة ط — الجودة والتقييم

1. مجموعة مهام مرجعية (golden tasks) لكل مجال، تُشغَّل مع كل تغيير.
2. قياس: هل نفّذ المطلوب؟ هل اختلق معلومات؟ هل احترم الموافقة؟
3. اختبارات انحدار للسلوك الخطر: أداة غير مسجّلة، مدخلات خاطئة، إعادة محاولة، رفض بلا موافقة.
4. مقارنة النماذج على نفس المهام لاختيار الأنسب لكل دور.

### المرحلة ي — التوزيع لكل الناس

1. تجربة أول استخدام: أول مهمة ناجحة في أقل من دقيقتين.
2. صفحات استخدام لكل مجال بلغة المستخدم، لا لغة تقنية.
3. خطط وأسعار واضحة مرتبطة بالاستهلاك الفعلي.
4. دعم داخل التطبيق ومحتوى تعليمي قصير.
5. إصدار Android/iOS مستقر + تحديثات OTA.

## 4. ترتيب التنفيذ المقترح

| الترتيب | الحزمة | لماذا الآن |
|---|---|---|
| 1 | محرك الأدوات + اختبار حي لـ Gmail | بدونها لا يمكن إضافة خدمات بسرعة |
| 2 | الذاكرة والتفضيلات | أكبر فرق في الإحساس بالذكاء |
| 3 | الاستمرارية والمهام المجدولة | يحوّل الوكيل من رد إلى خدمة |
| 4 | تكاملات Calendar/Drive/Sheets/GitHub | قيمة يومية مباشرة |
| 5 | تجربة المتابعة والموافقات | الثقة قبل التوسع |
| 6 | بيئة التنفيذ والملفات | قدرات أعمق |
| 7 | التقييم والتشغيل على نطاق | الاستقرار عند نمو المستخدمين |

## 5. مؤشرات النجاح

- نسبة المهام المكتملة بدون تدخل يدوي.
- نسبة الموافقات المرفوضة (مؤشر على وضوح المعاينة).
- متوسط زمن أول نتيجة مفيدة.
- نسبة الادعاءات غير الموثقة (يجب أن تقترب من الصفر).
- تكلفة الطلب مقابل القيمة المقدّمة.
- نسبة المستخدمين الذين يعودون لاستخدام الوكيل أسبوعيًا.

## 6. ما يحتاجه المشروع من صاحب المنتج

1. `SUPABASE_ACCESS_TOKEN` كـ GitHub Secret لتفعيل النشر التلقائي.
2. `EXPO_TOKEN` لتفعيل تحديثات OTA.
3. حسابات تجريبية للتكاملات (Gmail / Drive) لاختبار حي آمن.
4. قرار في الحدود التجارية: سقف التكلفة لكل مستخدم، والخطط.
5. أولوية المجالات المستهدفة أولًا، لتركيز التكاملات.

## 7. خلاصة صريحة

النواة جاهزة، والاتجاه واضح. الفرق بين «تطبيق شات ذكي» و«وكيل يخدم كل الناس» ليس نموذجًا أقوى، بل **أدوات أكثر + ذاكرة أطول + استمرارية + ثقة**. الثلاثة الأولى هندسية، والرابعة سياسة منتج.

لو نُفّذت الحزم 1–5 بالترتيب، سيصبح المنتج وكيلًا عمليًا يخدم مستخدمًا عاديًا في حياته اليومية، لا مجرد مساعد يجيب أسئلة.
