## 2. خط أساس المستودع والبنية

المكدس القائم الذي تمت مراجعته يتضمن Expo / React Native / React مع TypeScript، وSupabase PostgreSQL وEdge Functions.

المكونات الموجودة في المستودع:
- Central AI Router وAgent Orchestrator.
- توجيه نماذج حسب الأدوار: chat وplanner وworker وreviewer وsummarizer.
- Tool Registry يتضمن أدوات connected_app وweb.search، مع اشتراط موافقة لأداة الكتابة.
- Brain Router كطبقة استقبال/مصادقة/استخدام/حفظ نتائج وتفويض التنفيذ إلى AI Router.
- Persistent Task Queue مع claim وlease وheartbeat وretry/backoff وتسوية الحالات والإلغاء للمهام queued.
- Worker وScheduler موجودان، لكن نطاق المعالجة الحالي في الكود الذي تمت مراجعته يقتصر على `brain_task`.
- HIMS ونظام المحادثة والرصيد/الاستهلاك والذاكرة الحالية أنظمة قائمة يجب الحفاظ عليها.

## 4. نتائج مراجعة الأمن

أظهر تقرير Supabase Advisor:
- 12 تحذيرًا من نوع `rls_enabled_no_policy`.
- تحذيرين متعلقين بوجود extensions في schema عامة.
- تحذيرًا واحدًا لوظيفة SECURITY DEFINER متاحة لـ anon.
- 73 تحذيرًا لوظائف SECURITY DEFINER متاحة لـ authenticated.
- Leaked Password Protection غير مفعّل.
- تحذيرات أداء تشمل مفاتيح خارجية غير مفهرسة وفهارس غير مستخدمة وسياسات permissive متداخلة.

### تفسير النتائج والإجراء المطلوب

1. لا يعني غياب Policy على جدول أنه مكشوف تلقائيًا؛ يجب فحص grants وRLS وطريقة وصول الخدمات. بعض الجداول التي تمت مراجعتها داخلية ولا تملك grants مباشرة لـ anon/authenticated.
2. يجب مراجعة كل SECURITY DEFINER على حدة: المالك، وsearch_path، والتحقق من هوية المستدعي، والصلاحيات، وما إذا كان التنفيذ مقصودًا. لا تُجرى عمليات revoke جماعية.
3. تفعيل Leaked Password Protection تغيير أمني مرغوب، لكن يجب أولًا التحقق من إعدادات Auth الحالية وأثره على التسجيل وتغيير كلمات المرور، ثم تفعيله عبر إعدادات المشروع المعتمدة والتحقق منه.
4. تحذيرات الفهارس والأداء لا تُعالج ضمن دفعة أمنية عشوائية؛ تُراجع وفق استعلامات فعلية وخطة قياس.
5. لا توجد في هذه الدفعة تغييرات RLS أو grants أو وظائف SECURITY DEFINER أو إعدادات Auth.

### جداول الوكلاء وسياسات الوصول

تمت مراجعة سياسات وجداول منها:
- `agent_task_jobs` مع سياسة قراءة مرتبطة بـ `user_id = auth.uid()`.
- `agent_workspaces` و`agent_workspace_steps` و`agent_workspace_reviews` و`brain_task_contexts` و`brain_task_steps` و`task_ledger` مع سياسات قراءة مرتبطة بالمالك/المستخدم أو صلاحية الإدارة بحسب الجدول.
- `agent_step_usage` و`agent_tool_execution_checkpoints` لم يظهر لهما Policies أو grants مباشرة لـ anon/authenticated في الفحص المنفذ؛ يلزم توثيق نمط الوصول الخادمي قبل أي تعديل.

## 9. تحديث المرحلة 1 — نتائج التحقق الأمني (2026-11-19)

تم تنفيذ مراجعة أدق لحدود RPC وامتيازات قاعدة البيانات، وإضافة اختبارات Regression في:
`supabase/tests/agent_security_boundary_regression.sql`.

### نتائج التحقق الإضافي

- الجداول العامة التي عليها RLS بلا Policies لا تمنح أدوار `anon` أو `authenticated` صلاحيات مباشرة في الفحص الحالي.
- كل وظائف `SECURITY DEFINER` المكشوفة لـ `anon` أو `authenticated` لها `search_path` مضبوط في الفحص الحالي.
- لا توجد وظيفة `SECURITY DEFINER` متاحة لـ `anon` خارج نقطة مشاركة المحادثة المقصودة، والتي تتحقق من رمز المشاركة.
- وظائف الإدارة المكشوفة للمستخدم المسجل تتحقق من صلاحية المدير مباشرة أو تفوض إلى وظيفة محمية؛ واستثناء تحديث المزود يربط هوية المستدعي بعضوية المدير.
- وظائف المطالبة بالرصيد اليومي وقراءة الاشتراك تتحقق من تطابق المستخدم أو صلاحية المدير أو دور الخدمة.
- وظائف مشاركة المحادثات تتحقق من ملكية المحادثة.
- دالة موارد HIMS تتحقق من المستخدم النشط وتفعيل HIMS.
- اختبارات SQL للحدود أعلاه، واختبار صلاحيات إضافة مزود، واختبار موارد HIMS نُفذت دون أخطاء في جلسة الفحص. اختبارات SQL المعتمدة على `ROLLBACK` لا تحتفظ بتغييرات بيانات.

### إعداد حماية كلمات المرور المسربة

حالة منظمة Supabase الحالية هي الخطة المجانية (`tier_free`). توثيق Supabase الحالي يذكر أن ميزة Leaked Password Protection متاحة على Pro وما فوق؛ لذلك لم يتم تفعيلها أو محاولة تجاوز قيود الخطة. تبقى هذه النقطة **غير قابلة للمعالجة على الخطة الحالية**، ويجب إعادة تقييمها إذا تغيرت الخطة. المرجع: https://supabase.com/docs/guides/auth/password-security

### قرارات السلامة

- لم يظهر من الفحص الحالي خلل مثبت يبرر Migration أو تغيير RLS/GRANT؛ لذلك لم يتم تعديل المخطط أو الصلاحيات.
- تحذيرات Advisor الخاصة بوظائف `SECURITY DEFINER` المتاحة لـ `authenticated` لا تثبت وحدها وجود تجاوز صلاحيات؛ يجب قراءة الحماية داخل كل وظيفة. الاختبارات الجديدة تحرس مجموعة من هذه الحدود حتى لا تتراجع لاحقًا.
- تحذير RLS بلا Policy يصنفه Advisor حاليًا `INFO`، وتظل مراجعة grants جزءًا من شرط القبول.
- لم يتم تعديل HIMS أو إعدادات Auth أو أسرار المشروع.

### ما تبقى قبل قبول المرحلة 1

1. التحقق من إتمام CI وProduction deployment للـ commit الحالي.
2. إجراء اختبارات عزل حية بمستخدمين مستقلين على مسارات المهام والذاكرة والملفات والمحادثات، في بيئة اختبار معزولة لتجنب المساس ببيانات الإنتاج.
3. الحصول على صلاحية/مسار موثق لقراءة Auth config من Management API قبل الحكم على بقية إعدادات Auth؛ لا تتوفر أداة تعديل Auth config ضمن أدوات المشروع المتاحة في هذه الجلسة.
4. إعادة فحص Supabase Advisor بعد اكتمال الاختبارات، ثم إصدار تقرير قبول أو قائمة مخاطر متبقية.
