## 1. الرؤية والنتيجة المطلوبة

يتطور SULY من تجربة محادثة متعددة النماذج إلى **Autonomous Agent Platform**. يحدد المستخدم هدفًا أو مهمة، ثم يقوم النظام — وفق الصلاحيات والميزانية — بفهم المطلوب، ووضع خطة، واختيار النماذج والأدوات، وتنفيذ الخطوات في بيئات معزولة، والتحقق من النتائج، ومعالجة الإخفاقات، ثم تسليم مخرجات قابلة للاستخدام مع تقرير واضح.

المطلوب ليس تقليد واجهة منتج آخر، ولا الاكتفاء بإظهار رسائل توحي بالتنفيذ. معيار النجاح هو **إنجاز فعلي يمكن التحقق منه**.

### مبادئ لا تقبل التنازل

1. الحفاظ على هوية SULY وتجربة المستخدم الحالية.
2. الحفاظ على HIMS وجميع الأنظمة الحالية؛ لا حذف أو تعطيل أو استبدال ضمني.
3. الأمن والخصوصية والصلاحيات جزء من التصميم منذ البداية.
4. كل تنفيذ يجب أن يكون قابلًا للتتبع والاستئناف والإلغاء والمراجعة.
5. لا يُدّعى إنجاز أي قدرة قبل وجود دليل واختبارات.
6. استخدام النماذج والأدوات بتوجيه مركزي، مع عدم افتراض أن نموذجًا واحدًا مناسب لكل المهام.
7. المحادثة العادية تظل سريعة؛ لا يتم تشغيل منظومة الوكلاء الثقيلة إلا عند الحاجة أو بطلب المستخدم.
8. تصميم مرن للتكاليف والحصص ومزودي النماذج، دون ربط النظام بمزود واحد.

هذه أهداف تطوير وليست ادعاءً بأن SULY يمتلكها حاليًا أو أنه سيطابق Manus في كل معيار.

## 3. المعمارية المستهدفة

### 3.1 طبقة التطبيق والواجهات
- تطبيق SULY الحالي متعدد المنصات.
- واجهة محادثة وواجهة Agent Tasks تعرض الخطة والحالة والمخرجات.
- واجهات إدارة منفصلة حسب الدور، دون كشف أدوات الإدارة للمستخدم العادي.
- واجهات API موحدة ومتحقق من صلاحياتها.

### 3.2 Central Agent / Orchestrator
المسؤول عن:
- استقبال الطلب والسياق والقيود والميزانية.
- تحديد هل الطلب محادثة عادية أم مهمة Agent.
- إنشاء معرف مهمة ثابت وتسجيلها.
- إدارة دورة الحياة: `queued → planning → running → verifying → completed/failed/cancelled`.
- توزيع العمل ومراقبة الوكلاء وإدارة الإلغاء وإعادة المحاولة.
- منع تنفيذ نفس العملية مرتين عند إعادة إرسال الطلب (Idempotency).

### 3.3 Planner وDAG
- يحول الهدف إلى خطة منظمة من خطوات.
- يمثل الاعتماديات في Directed Acyclic Graph (DAG).
- يحدد لكل خطوة المدخلات والمخرجات والأداة المطلوبة والمهلة والمخاطر والتكلفة التقديرية.
- يكتشف التعارضات والخطوات غير القابلة للتنفيذ.
- يطلب توضيحًا من المستخدم عندما تكون معلومة أساسية مفقودة.
- لا يسمح بتجاوز موافقات المستخدم المطلوبة.

### 3.4 Multi-Agent Runtime
وكلاء متخصصون محتملون، ويُفعّل كل منهم عند الحاجة:
- Research Agent: البحث وجمع الأدلة.
- Planning Agent: التخطيط وتحليل الاعتماديات.
- Coding Agent: تعديل وكتابة الأكواد.
- Browser Agent: التصفح والتفاعل المسموح.
- Data Agent: تحليل البيانات والاستعلامات المصرح بها.
- Testing Agent: الاختبارات والتحقق.
- Review/Security Agent: مراجعة المخرجات والمخاطر.

كل وكيل يعمل بعقد واضح: المهمة، السياق المسموح، الأدوات المتاحة، حد الوقت، حد التكلفة، والمخرجات المتوقعة. لا يحصل الوكيل تلقائيًا على كل صلاحيات النظام.

### 3.5 Tool Registry
- سجل مركزي للأدوات مع الاسم والإصدار والوصف ومخطط المدخلات والمخرجات.
- تصنيف حسب المخاطر والصلاحيات.
- تحقق صارم من المدخلات والمخرجات.
- مهلات زمنية وحدود حجم ومعدل الاستخدام.
- تسجيل هوية الوكيل والمستخدم والمهمة عند كل استدعاء.
- إيقاف الأدوات أو إصداراتها عند اكتشاف خلل.

أمثلة تكاملات مستقبلية: GitHub، Supabase، خدمات الملفات، البحث، APIs، بيئة Terminal معزولة، والمتصفح السحابي.

### 3.6 Execution Engine وبيئات التشغيل
- تنفيذ الأعمال داخل حاويات أو بيئات معزولة قصيرة العمر حسب نوع المهمة.
- عدم تشغيل كود غير موثوق داخل خادم التطبيق الأساسي.
- حدود CPU والذاكرة والوقت ومساحة التخزين والشبكة.
- نظام ملفات مؤقت مع قواعد واضحة لحفظ المخرجات.
- منع الوصول إلى أسرار النظام أو بيانات مستخدم آخر.
- تسجيل stdout/stderr والنتائج والأخطاء دون تسجيل الأسرار.
- تنظيف البيئة بعد انتهاء المهمة، مع الاحتفاظ بالمخرجات المصرح بها فقط.

### 3.7 Browser / Computer Engine
- جلسات متصفح معزولة لكل مهمة أو سياق موثوق.
- قائمة سماح/حظر للنطاقات حسب السياسة.
- حماية من SSRF والوصول إلى عناوين الشبكات الداخلية وواجهات metadata.
- التعامل مع تسجيل الدخول والبيانات الحساسة بموافقة المستخدم.
- لا يتم تنفيذ شراء أو نشر أو حذف أو إرسال خارجي حساس دون موافقة مناسبة.
- لقطات/سجلات عملية بالقدر الضروري، مع مراعاة الخصوصية والاحتفاظ المحدود.

### 3.8 Model Gateway وModel Router
- نقطة اتصال موحدة لمزودي النماذج.
- توحيد تنسيق الرسائل والأدوات والأخطاء والاستخدام.
- اختيار النموذج بناءً على نوع المهمة والجودة والسرعة والتكلفة والتوفر.
- دعم fallback آمن عند تعطل المزود، دون تكرار عمليات ذات آثار جانبية.
- تسجيل اسم المزود والنموذج والإصدار والاستهلاك الفعلي.
- حماية مفاتيح API في الخادم أو مخزن أسرار؛ لا تُضمّن مفاتيح خاصة في تطبيق العميل أو المستودع.
- عدم الادعاء بأن النموذج نفذ أداة ما لم يرجع تنفيذ الأداة نتيجة موثقة.

### 3.9 Memory وProject Context
- فصل ذاكرة المستخدم عن ذاكرة المشروع وعن سجل المهمة.
- عزل صارم حسب المستخدم/المؤسسة/المشروع.
- تحديد ما يُحفظ ولماذا ومدة الاحتفاظ به.
- إتاحة مراجعة الذاكرة وتصحيحها وحذفها وفق سياسة المنتج.
- عدم تخزين كلمات المرور أو مفاتيح API أو بيانات الدفع الحساسة في الذاكرة.
- استرجاع السياق ذي الصلة فقط، مع إظهار مصدره عند الحاجة.

### 3.10 Persistent Task Queue
- طابور مهام دائم مع حالات قابلة للاستئناف.
- Workers قابلة للتوسع أفقيًا.
- Heartbeats ومهل زمنية واكتشاف المهام المتوقفة.
- Retry policy محددة مع Exponential Backoff وDead-letter queue.
- إلغاء آمن للمهام والعمليات الفرعية.
- حفظ checkpoints بعد الخطوات المهمة.
- ضمان عدم تكرار الخصم أو الآثار الجانبية عند إعادة المحاولة.

### 3.11 Verification وSelf-Correction
- تعريف معيار نجاح لكل مهمة قبل التنفيذ.
- فحص المخرجات باستخدام اختبارات أو مصادر أو أدوات مستقلة قدر الإمكان.
- تصنيف الأخطاء: مؤقتة، مدخلات، صلاحيات، نموذج، أداة، أو بنية تحتية.
- السماح بمحاولات إصلاح محدودة بميزانية وزمن.
- إيقاف المحاولات عند تجاوز الحدود أو ارتفاع المخاطر.
- عرض ما نجح وما فشل وما لم يتم التحقق منه بوضوح.

## 4. التكامل مع النظام الحالي

قبل أي تغيير، يجب إعداد خريطة موثقة للمعمارية الحالية تشمل:
- Expo / React / TypeScript وتدفقات التطبيق.
- Supabase Auth وDatabase وStorage وEdge Functions إن وجدت.
- الجداول والعلاقات والفهارس وسياسات RLS.
- المحادثات والرسائل والذاكرة والملفات.
- HIMS وكل وظائفه وتبعياته.
- نظام الرصيد والكريدت وسجل الاستهلاك.
- إعدادات النماذج ومزوديها.
- لوحة الإدارة والأدوار والصلاحيات.
- النشر والبناء والاختبارات الحالية.

### قواعد التكامل
1. لا تنشئ نظام Auth موازيًا إذا كان الحالي يفي بالغرض.
2. لا تنشئ جداول بديلة قبل فحص الجداول الحالية وإمكانية توسيعها.
3. أي Migration يجب أن تكون قابلة للمراجعة وآمنة وقابلة للاسترجاع قدر الإمكان.
4. لا تغيّر عقود API المستخدمة حاليًا دون توافق خلفي وخطة انتقال.
5. لا تحذف HIMS أو تعطل وظائفه أو تغير صلاحياته دون موافقة صريحة.
6. حافظ على تجربة المحادثة الحالية أثناء إدخال وضع الوكلاء تدريجيًا.

## 5. الأمن والخصوصية

### 5.1 الهوية والصلاحيات
- الاعتماد على نظام الهوية المعتمد حاليًا بعد مراجعته.
- RBAC للأدوار وABAC للسياق عند الحاجة.
- مبدأ أقل صلاحية (Least Privilege).
- التحقق من الصلاحيات على الخادم في كل عملية، وليس في الواجهة فقط.
- MFA إلزامي للحسابات الإدارية الحساسة متى كان مدعومًا.
- فصل صلاحيات المستخدم والدعم والإدارة والمالك.

### 5.2 عزل البيانات
- RLS لكل الجداول التي تحتوي بيانات مستخدمين أو مشاريع.
- اختبارات سلبية لمحاولات الوصول بين المستخدمين.
- عدم الثقة بمعرفات المستخدم القادمة من العميل؛ استخرج الهوية من جلسة موثوقة.
- فصل أسرار الخدمات عن بيانات التطبيق.
- مراجعة سياسات Storage وعمليات التنزيل والرفع.

### 5.3 حماية الوكلاء والأدوات
- اعتبار محتوى المواقع والملفات والرسائل الخارجية بيانات غير موثوقة.
- مقاومة Prompt Injection وعدم اعتبار النص الخارجي تعليمات نظام.
- فحص المدخلات والمخرجات وتقييد الأدوات.
- SSRF protection وقيود الشبكة.
- منع Command Injection وPath Traversal وSQL Injection.
- عدم تمرير أسرار إلى النماذج أو السجلات دون ضرورة وموافقة.
- مراجعة الملفات قبل تشغيلها أو تنفيذ محتواها.

### 5.4 الموافقات حسب مستوى المخاطر

| المستوى | أمثلة | السياسة |
|---|---|---|
| منخفض | تلخيص، بحث عام، إنشاء مسودة | تنفيذ ضمن حدود المهمة |
| متوسط | تعديل ملفات مشروع في مساحة عمل | تأكيد النطاق أو صلاحية مسبقة واضحة |
| مرتفع | نشر، إرسال رسائل خارجية، تعديل بيانات مهمة | موافقة صريحة قبل التنفيذ |
| حرج | مدفوعات، حذف دائم، تغيير صلاحيات المالك، كشف أسرار | منع افتراضيًا أو موافقة مشددة مع سجل تدقيق |

### 5.5 التدقيق والاستجابة
- Audit log غير قابل للتعديل من واجهة المستخدم العادية.
- تسجيل الفاعل والوقت والمورد والقرار ونتيجة العملية.
- تنبيهات للأنشطة غير المعتادة.
- خطة للتعامل مع تسرب الأسرار أو إساءة استخدام الأدوات.
- نسخ احتياطية واختبار الاستعادة.
- سياسة احتفاظ وحذف واضحة.

## 6. الأدوار الإدارية

يجب أن تكون الصلاحيات محددة ومختبرة، لا تعتمد على إخفاء الأزرار فقط:

- **User:** إدارة بياناته ومهامه ومشاريعه المصرح بها.
- **Project Member:** صلاحيات محدودة داخل مشروع وفق عضويته.
- **Support:** دعم وتشخيص محدود، دون الاطلاع الافتراضي على محتوى خاص غير مطلوب.
- **Admin:** إدارة وظائف تشغيلية محددة وفق صلاحيات مفصلة.
- **Owner / Super Admin:** إعدادات المنصة الحساسة، مع MFA وتسجيل تدقيق ومراجعة إضافية.

يجب تحديد من يستطيع: إدارة المستخدمين، النماذج، مزودي الخدمة، الأدوات، الكريدت، السياسات، سجلات التدقيق، HIMS، والنشر. لا تمنح جميع الصلاحيات لحساب إداري واحد دون ضرورة.

## 7. الكريدت والتكلفة والفوترة

- إنشاء Usage Ledger موحد باعتباره مصدر الحقيقة للاستهلاك.
- تسجيل التكلفة الفعلية لكل استدعاء نموذج وأداة وبيئة تشغيل.
- فصل التقدير المسبق عن الاستهلاك الفعلي.
- حجز رصيد عند بدء المهمة وتسوية الاستهلاك عند انتهائها وفق سياسة معلنة.
- استخدام مفاتيح Idempotency لمنع الخصم المكرر.
- دعم Partial Billing للمهام التي أنجزت بعض خطواتها فقط.
- عدم خصم تكلفة خطوة لم تنفذ.
- معالجة حالات timeout وانقطاع المزود والنتائج المكررة.
- إظهار تقدير التكلفة قبل المهام المكلفة، ثم التكلفة النهائية بعد التنفيذ.
- وضع سقوف لكل مستخدم ومهمة ووكيل ومزود.
- لا يتم تغيير أسعار الخطط أو قواعد الكريدت الحالية دون قرار موثق واختبارات ترحيل.

## 9. خطة التنفيذ المرحلية

| المرحلة | النطاق | مخرجات القبول |
|---|---|---|
| 0 | تدقيق المستودع والنظام الحالي | خريطة معمارية، قائمة مخاطر، baseline للاختبارات، توثيق HIMS |
| 1 | أساس الأمان والبيانات | مراجعة Auth/RLS/RBAC/Secrets ونسخ احتياطية واختبارات عزل |
| 2 | عقود Agent وTask | نماذج بيانات وحالات مهمة وواجهات API موثقة |
| 3 | Central Agent | توجيه الطلبات وإدارة دورة حياة المهمة |
| 4 | Planner وDAG | خطط قابلة للتحقق واعتماديات صحيحة |
| 5 | Queue وWorkers | مهام دائمة وcheckpoint واستئناف وإلغاء آمن |
| 6 | Tool Registry | سجل أدوات ومخططات وصلاحيات وتدقيق |
| 7 | Execution Sandbox | تشغيل معزول وحدود موارد وتنظيف آمن |
| 8 | Model Gateway | توحيد المزودين والتوجيه والـ fallback وتسجيل الاستخدام |
| 9 | Multi-Agent Runtime | وكلاء متخصصون وتنسيق وتبادل مخرجات مضبوط |
| 10 | Browser Engine | تصفح معزول وحماية SSRF وموافقات |
| 11 | Memory وProject Context | ذاكرة معزولة وسياسات حفظ وحذف |
| 12 | Verification وRecovery | تحقق مستقل وإصلاح محدود وإيقاف آمن |
| 13 | Credits وUsage Ledger | فوترة دقيقة ومنع الخصم المكرر وتسوية |
| 14 | واجهة Agent | عرض الخطة والتقدم والموافقات والنتائج |

## 10. سياسة GitHub والعمل على الإنتاج

**هذه القواعد إلزامية لكل مطور أو وكيل آلي يعمل على المستودع:**

1. العمل على فرع الإنتاج المعتمد حاليًا فقط: `release/v1`.
2. ممنوع إنشاء أي فرع جديد لهذا العمل.
3. ممنوع الانتقال إلى فرع آخر أو تعديل أي فرع آخر.
4. قبل كل دفعة تغييرات، تحقق من اسم الفرع وHEAD الحالي وحالة الملفات.
5. لا تفترض أن الفرع ما زال كما كان في آخر جلسة؛ أعد التحقق.
6. لا تنفذ Force Push أو History Rewrite.
7. لا ترفع أسرارًا أو ملفات بيئة أو مفاتيح API أو بيانات مستخدمين.
8. لا تدمج تغييرات واسعة أو غير مرتبطة بالمهمة.
9. افحص Diff قبل كل Commit، وشغّل الاختبارات المناسبة.
10. استخدم رسائل Commit واضحة ومحددة.
11. احتفظ بنقطة رجوع وخطة Rollback لكل تغيير مؤثر.
12. لا تنشر إصدارًا إنتاجيًا تلقائيًا إلا إذا كان ذلك مطلوبًا ومصرحًا به صراحة.
13. إذا تعذر التحقق من الفرع أو تعارضت التغييرات، توقف واطلب مراجعة بدل التخمين.

### حدود التغيير
- لا حذف أو إعادة تسمية جماعية للملفات دون مبرر موثق.
- لا استبدال كامل لمكونات قائمة لمجرد تفضيل تصميم جديد.
- لا تغيير مخطط قاعدة البيانات مباشرة في الإنتاج دون Migration ومراجعة.
- لا تعطيل HIMS أو Auth أو RLS أو نظام الكريدت أو المحادثات أو الذاكرة.
- يجب أن تكون التغييرات متوافقة خلفيًا أو تتضمن خطة انتقال واختبار.

## 11. الاختبارات المطلوبة

### Functional
- طلب بسيط يظل ضمن مسار المحادثة السريع.
- مهمة متعددة الخطوات تنتج خطة صحيحة.
- تنفيذ خطوة يعتمد على مخرجات خطوة سابقة.
- مهمة طويلة تستأنف بعد انقطاع Worker.
- الإلغاء يمنع الخطوات اللاحقة غير الضرورية.
- النتائج المعروضة تطابق الملفات والمخرجات الفعلية.

### Security
- مستخدم لا يستطيع قراءة أو تعديل بيانات مستخدم آخر.
- الوكيل لا يستطيع استدعاء أداة خارج صلاحياته.
- محتوى Prompt Injection لا يرفع الصلاحيات.
- منع SSRF والوصول إلى الشبكات الداخلية.
- الأسرار لا تظهر في العميل أو السجلات أو Git.
- العمليات الحساسة تتطلب موافقة مناسبة.
- صلاحيات الإدارة وHIMS مختبرة باختبارات إيجابية وسلبية.

### Reliability وBilling
- إعادة الطلب لا تنشئ تنفيذًا مكررًا أو خصمًا مزدوجًا.
- تعطل مزود النموذج يعالج دون فساد حالة المهمة.
- المهلة وإعادة المحاولة محددتان.
- كل استهلاك مسجل ويمكن مطابقته مع Usage Ledger.
- لا تظهر المهمة مكتملة قبل اجتياز معايير التحقق.

### Performance
- قياس زمن بدء المهمة وزمن كل خطوة.
- قياس استهلاك الذاكرة والمعالج والتخزين.
- قياس التكلفة لكل نوع مهمة.
- اختبار التزامن وحدود الطوابير.
- تحديد SLOs واقعية بعد قياس baseline، لا اختراع أرقام دون اختبار.

## 12. مؤشرات القياس (KPIs)

- Task Success Rate: نسبة المهام التي اجتازت معايير القبول.
- Verified Completion Rate: نسبة المهام التي تم التحقق من نتائجها.
- Recovery Rate: نسبة الإخفاقات التي تعافت دون تدخل.
- Median / P95 Task Duration.
- Cost per Successful Task.
- Duplicate Execution / Duplicate Charge Rate.
- Tool Failure Rate.
- User Approval Rate للعمليات الحساسة.
- Security Findings المفتوحة والمغلقة.
- Availability للـ Queue والـ Workers والـ Model Gateway.

يجب تسجيل قيمة البداية ثم مقارنة كل إصدار بها.

## 13. سجل الإنجاز ونسبة التقدم

لا تُحسب نسبة الإنجاز من عدد الملفات أو الأسطر أو commits. لكل مرحلة:
- المتطلبات المنفذة.
- المتطلبات غير المنفذة.
- الاختبارات التي نجحت وفشلت.
- روابط أو معرفات Commits.
- Migrations ونتائجها.
- المخاطر المفتوحة.
- دليل التشغيل أو لقطة النتيجة عند الحاجة.

### مقياس الإنجاز
- 0%: لم يبدأ التنفيذ.
- 25%: التصميم والتدقيق جاهزان.
- 50%: التنفيذ الأساسي موجود لكن الاختبارات غير مكتملة.
- 75%: الوظائف مكتملة والاختبارات الأساسية ناجحة.
- 90%: اختبارات التكامل والأمان والأداء مقبولة.
- 100%: جميع معايير القبول موثقة، والإطلاق والمراقبة والرجوع مجربة.

يجب أن تكون النسبة موزونة بمتطلبات المرحلة، لا تقديرًا انطباعيًا. لا تمنح 100% عند وجود ثغرة حرجة أو اختبار قبول أساسي فاشل.

### قالب تقرير كل مرحلة

```text
اسم المرحلة:
الحالة: لم تبدأ / قيد التنفيذ / مكتملة / متوقفة
نسبة الإنجاز:
نطاق التغيير:
الملفات المتأثرة:
قاعدة البيانات / Migrations:
الاختبارات المنفذة:
نتائج الاختبارات:
نتائج مراجعة الأمن:
Commit SHA:
المخاطر أو القيود:
خطة Rollback:
قرار الانتقال للمرحلة التالية:
```

## 14. شروط الإيقاف والتصعيد

يجب إيقاف التنفيذ فورًا عند:
- اكتشاف تسريب أسرار أو بيانات مستخدمين.
- فشل RLS أو ظهور وصول بين حسابات مختلفة.
- احتمال حذف أو تعطيل HIMS أو نظام أساسي.
- عدم وضوح فرع الإنتاج أو وجود تغييرات متعارضة.
- Migration قد تسبب فقد بيانات دون خطة استعادة.
- تنفيذ عملية حساسة دون موافقة.
- خصم رصيد غير صحيح أو متكرر.
- عدم القدرة على التحقق من نتيجة العملية.

يتم توثيق المشكلة والأثر وخيارات الإصلاح قبل الاستمرار.

## 15. تعريف الإنجاز النهائي

لا تعتبر المنصة مكتملة لمجرد وجود Planner أو Agents في الكود. يلزم إثبات رحلة متكاملة واحدة على الأقل لكل فئة مدعومة، من طلب المستخدم حتى تسليم نتيجة فعلية، وتشمل:

1. فهم المهمة وتحديد قيودها.
2. إنشاء خطة واعتماديات.
3. اختيار نموذج وأدوات مناسبة.
4. تنفيذ فعلي داخل بيئة آمنة.
5. حفظ التقدم وإمكانية الاستئناف.
6. التحقق من المخرجات وتصحيح الأخطاء ضمن حدود.
7. فرض الموافقات والصلاحيات.
8. تسجيل الاستهلاك والتكلفة بدقة.
9. عرض تقرير نهائي صادق يميز بين المكتمل وغير المكتمل.
10. إثبات عدم تأثر HIMS والأنظمة القائمة.

**النتيجة المستهدفة:** SULY منصة وكلاء قوية وقابلة للتوسع، قادرة على تنفيذ مهام متعددة الخطوات بأمان وشفافية، وتطوير قدراتها تدريجيًا بناءً على نتائج واقعية. الوصول إلى مستوى منتج مثل Manus هدف تنافسي يُقاس باختبارات معيارية مستمرة، وليس وعدًا تلقائيًا بمجرد إتمام هذه الوثيقة.

## 16. تعليمات تنفيذ مختصرة للمطور أو وكيل البرمجة

ابدأ بالمرحلة 0 فقط. افحص المستودع والتطبيق وقاعدة البيانات والتدفقات الحالية، وحدد الفرع `release/v1` وتحقق من HEAD قبل أي تعديل. لا تنشئ فروعًا. لا تبدأ إعادة هيكلة أو كتابة كود قبل تقديم تقرير التدقيق وخريطة الأنظمة والمخاطر وخطة التنفيذ التفصيلية. حافظ على HIMS وكل الوظائف الحالية. بعد اعتماد التدقيق، نفّذ مرحلة واحدة في كل مرة، واختبرها ووثق Commit SHA والنتائج ونسبة الإنجاز الفعلية قبل الانتقال إلى التالية.
